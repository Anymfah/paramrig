# Prompt pré-publication 1 : plus de surprise avant le paquet npm

> Document autonome : un agent qui démarre sans contexte doit pouvoir l'exécuter de bout en bout. L'état de référence est le code, pas ce document.

Tu es un agent qui démarre sans aucun contexte. Tout ce dont tu as besoin est ici ou dans le dépôt ; ne suppose rien, vérifie dans le code.

Dépôt : `/Users/soheil/Documents/repos/paramrig`, branche `main`, distant `github.com/Anymfah/paramrig`. ParamRig est un workbench où une IA construit des rigs paramétrés qu'un humain règle avec des contrôleurs. La voie « situation réelle » du produit est l'atelier Web : un projet tiers installe le SDK `@paramrig/web`, décrit ses contrôles dans `.paramrig/manifest.json`, et le workbench ouvre sa page de développement dans une iframe cross-origin ; l'humain règle, sélectionne, commente, valide un lot que l'agent du projet lit sur disque. Trois morceaux : l'hôte React (`src/web/`), le SDK injecté dans la page cible (`src/web/sdk.ts`, `contracts.ts`, `geometry.ts`, compilé par `npm run build:web-sdk` vers `packages/web-sdk/`), et le service de fichiers (`services/web/server.mjs`, profil Compose `web`, proxy Vite sur `/api/web`). L'exemple Fieldnotes vit dans `examples/web/` et `src/web/example/`, ses fichiers de retours dans `.local/web/.paramrig/` (ignoré par git). Lis `docs/web-workspace.md`, `docs/web-workspace-prompt-1-bilan.md`, `e2e/README.md` et `AGENTS.md` en entier avant de commencer.

Ce prompt ne construit pas le paquet npm ni la ligne de commande qui l'accompagnera. Il enlève ce qui, mesuré le 6 septembre 2026, ferait surprise au moment de publier : le SDK qui casse ou salit la page du projet dans deux situations ordinaires, un piège Compose qui écrit dans un projet étranger, un paquet qui embarque des fichiers du workbench, et un dépôt sans licence, sans intégration continue, avec 6 Mo de captures suivies par erreur. Tout ce qui est mesuré dans le diagnostic a été reproduit dans le navigateur ou dans Docker ce jour-là ; reproduis-le avant de toucher au code.

## 0. Diagnostic de départ (mesuré le 6 septembre 2026, à reproduire avant de toucher au code)

- **Le SDK parle hors iframe.** La page de l'exemple ouverte seule sur 9223 (`http://127.0.0.1:5174/examples/web/index.html`, `window.parent === window`) journalise à chaque chargement `Failed to execute 'postMessage' on 'DOMWindow': The target origin provided ('http://localhost:5174') does not match the recipient window's origin ('http://127.0.0.1:5174')`. Cause : `src/web/sdk.ts:423` poste l'annonce `sdk-present` à `window.parent` sans regarder si la page est encadrée. Aucun overlay n'est créé, ce qui est juste ; l'avertissement, lui, sera vu par le développeur du projet à chaque rechargement de sa journée.
- **Un alias d'hôte rend la page blanche.** La même page ouverte par `http://localhost:5174/examples/web/index.html` : `#root` reste vide, `pageerror` « Check the ParamRig host and project origins. », et React avertit « An error occurred in the <Demo> component ». Cause : `src/web/sdk.ts:15` lance une exception quand `manifest.origin !== location.origin`, dans l'effet React qui appelle `connectWeb`, et l'application entière se démonte. Un projet réel répond par `localhost` et par `127.0.0.1` indifféremment ; une intégration réservée au développement ne doit jamais retirer l'application de l'écran.
- **L'origine du workbench est en dur.** `docs/web-workspace.md` fait écrire `hostOrigin: 'http://localhost:5174'` ; `src/web/example/Demo.tsx` aussi. Un workbench ouvert par `127.0.0.1:5174` n'appaire jamais, en silence, et après 8 s le message de `src/web/WebWorkspace.tsx:239` dit « Preview unavailable or SDK missing. Check the page URL and frame permissions. » sans nommer cette cause, qui est la plus probable dans un projet réel.
- **Le seed du manifeste est activé par défaut.** `compose.yml:45` : `PARAMRIG_SEED_MANIFEST: ${PARAMRIG_SEED_MANIFEST-/workspace/examples/web/manifest.json}`. Pointer un projet réel avec `PARAMRIG_PROJECT_DIR=/chemin docker compose --profile web up -d` sans écrire `PARAMRIG_SEED_MANIFEST=` copie le manifeste Fieldnotes dans ce projet, par `link` donc immuable, et le workbench ouvre « Fieldnotes » en essayant d'encadrer `127.0.0.1:5174`. Le service écrit ses fichiers en mode 0600 (`ls -la .local/web/.paramrig/batches` : `-rw-------`) en tant qu'utilisateur `node`, uid 1000 : sous Linux, avec un autre uid hôte, l'agent du projet ne peut pas lire ses propres lots. Ce dernier point est déduit du code et des modes observés, pas vérifié sur Linux.
- **Le paquet SDK embarque le workbench.** `find packages/web-sdk/dist -type f` après `npm run build:web-sdk` : `.htaccess`, `favicon.svg`, `fonts/PublicSans.ttf` (104 K), `fonts/PublicSans.woff2` (44 K), `fonts/PublicSans-OFL.txt`, à côté de `paramrig-web.js`, `index-L3Zm-CoX.js` (le chunk `html-to-image`) et des `.d.ts` de `web/` et `rigs/`. Cause : `vite.web-sdk.config.ts` n'a pas `publicDir: false`, et `emptyOutDir: false` laissera s'accumuler les anciens chunks à chaque changement de hash. `packages/web-sdk/package.json` déclare `files: ["dist"]` : tout cela partirait dans le paquet. Il est `private: true`, sans `license`, `repository`, `homepage`, `keywords`, `sideEffects`, sans README, et son `exports` n'a pas de condition `default`. Le paquet consommé depuis un projet tiers fonctionne par ailleurs : un `tsc` de consommateur résout les types, et l'entrée ESM exporte `connectWeb` et `parseManifest`.
- **Le dépôt.** Aucun fichier `LICENSE` (`find . -maxdepth 2 -iname 'LICENSE*' -not -path './node_modules/*'` ne renvoie rien) alors que le README dit « open-source » et qu'aucun `package.json` n'a de champ `license`. `git ls-files output | wc -l` : 59 captures PNG, 6,2 Mo, suivies à la racine dans `output/playwright/`, référencées nulle part (le README pointe `workproduct/ui-implementation/qa/`). Pas de `.github` : la chaîne de vérification est une discipline d'agent, pas une barrière. Pas de champ `engines` alors que le service exige Node 22.6 ou plus pour le strip-types. `docs/web-workspace-roadmap-prompt.md` n'est pas suivi alors que son bilan l'est.
- **Le site public.** `public/.htaccess:7` ne réécrit que `r/*`, `docs` et `docs/controls` : un rechargement de `/web`, `/docs/vector-rigs` ou `/docs/scene-rigs` sur l'hébergement de la démo tombera en 404 Apache. `src/library/LibraryPage.tsx:179` lie vers `https://paramrig.com/docs/persistence/` ; le 6 septembre `paramrig.com` a un enregistrement A mais refuse la connexion HTTPS (`curl -sI https://paramrig.com/` sans réponse, `http://` redirige vers `www.paramrig.com`), et `demo.paramrig.com` n'a pas d'enregistrement DNS. Le site n'est pas dans ce dépôt : ce prompt ne le répare pas, il le consigne.

## Chantier A · Le SDK ne surprend plus l'intégrateur

- **Hors iframe, il ne fait rien.** Quand `window.parent === window`, `connectWeb` ne pose aucun écouteur, aucun observateur, ne poste rien, et rend une connexion dont `dispose()` est inoffensif. Rien dans la console. La page d'un projet ouverte normalement ne doit porter aucune trace du SDK.
- **Une origine qui ne correspond pas ne casse jamais l'application.** Si `manifest.origin !== location.origin`, ou si l'option d'hôte est invalide, `connectWeb` écrit un seul `console.warn` qui nomme les deux origines et ce qu'il faut corriger, puis rend la même connexion inoffensive. `parseManifest` continue de lancer : un manifeste invalide est une erreur de programmation que l'intégrateur appelle lui-même, et la doc le dit. Regarde aussi ce qui se passe quand `connectWeb` est appelé deux fois sans `dispose` (rechargement à chaud mal écrit) : deux overlays ne doivent pas coexister ; choisis entre remplacer la précédente et refuser la seconde avec un avertissement, et dis pourquoi.
- **L'origine du workbench n'est plus en dur.** `hostOrigin` accepte une chaîne ou une liste, et devient optionnel avec pour défaut `['http://localhost:5174', 'http://127.0.0.1:5174']`. Pour que l'annonce atteigne un hôte quel que soit son alias sans avertissement, elle est postée avec la cible `'*'` : elle ne contient rien de secret (identifiant de projet et identifiant d'instance aléatoire), la session s'ouvre sur le `hello` reçu, dont l'origine doit appartenir à la liste, et tout message ultérieur est vérifié contre cette origine et cette session, en entrée comme en sortie. Écris ce raisonnement dans la section Pairing de `docs/web-workspace.md`. Si tu trouves un moyen de connaître l'origine du parent avant de poster (`location.ancestorOrigins`, absent de Firefox, ou `document.referrer`), utilise-le pour poster à l'origine exacte quand elle est connue et à `'*'` sinon, et dis-le. `src/web/example/Demo.tsx` et la doc n'écrivent plus `hostOrigin`.
- **Le workbench dit ce qui manque.** Le message après 8 s liste les trois causes dans l'ordre de probabilité : le serveur de développement ne répond pas à l'origine du manifeste, la page n'embarque pas le SDK ou refuse cette origine de workbench, l'encadrement est bloqué par la CSP ou `X-Frame-Options`. Mieux : une annonce reçue sans `ready` dans les 2 s qui suivent le `hello` est un cas distinct, « The page's SDK is present but did not accept this workbench origin (http://127.0.0.1:5174) », puisque l'hôte reçoit désormais l'annonce même quand le SDK ne l'accepte pas.
- **Tests** : `sdk.test.ts` (rien de posé hors iframe ; avertissement et non-exception sur une origine qui ne correspond pas ; liste d'hôtes et défaut ; `hello` d'une origine hors liste ignoré ; double `connectWeb`), un test de l'hôte pour le nouveau message, et `web-sdk-guard.e2e.mjs` : la page de l'exemple ouverte seule sans un seul message console venant du SDK et sans élément `paramrig-overlay` ; la même page par `localhost` rendue entière avec exactement un avertissement qui nomme les deux origines ; l'atelier ouvert par `http://127.0.0.1:5174/r/web-fieldnotes` qui appaire aussi vite que par `localhost` (mesure-le comme `web-connect` le fait).

## Chantier B · Le service et Compose face à un projet étranger

- **Oublier une variable n'écrit jamais dans un projet étranger.** Le seed du manifeste Fieldnotes ne concerne que l'exemple. Deux mécanismes candidats : le service ne seed que dans un répertoire vide ou ne contenant que `.paramrig` (un projet réel a un `package.json`, l'exemple n'a rien) ; ou l'exemple obtient son propre profil et son propre service Compose avec l'alias réseau `web`, et le service générique n'a aucun seed par défaut. Choisis le plus simple qui rende `PARAMRIG_PROJECT_DIR=/chemin docker compose --profile web up -d` sûr sans autre variable, et dis pourquoi. Un projet sans manifeste garde le message existant, « No web manifest found. Add .paramrig/manifest.json to the connected project. », et `/web` doit l'afficher tel quel avec le chemin attendu.
- **Les fichiers écrits appartiennent à l'utilisateur hôte.** Fais tourner le service `web` sous l'uid et le gid de l'hôte quand ils sont fournis (`user: "${PARAMRIG_UID:-1000}:${PARAMRIG_GID:-1000}"` ou équivalent), vérifie sur macOS que rien ne change, documente la variable pour Linux dans `docs/web-workspace.md` et `docs/local-docker-development.md`, et dis dans le bilan que Linux n'a pas été testé ici. Ne relâche pas les modes de fichiers pour contourner le problème.
- **Ce qu'on commite dans `.paramrig/`.** Le service écrit une fois, comme il écrit `README.md`, un `.paramrig/.gitignore` qui ignore `draft.json` et `captures/`, et laisse `manifest.json`, `batches/` et `responses/` au choix du projet ; le guide du chantier D explique ce choix. Si tu juges qu'écrire un `.gitignore` chez autrui dépasse ce que le service doit faire, ne l'écris pas et mets la recommandation dans le guide et dans `README.md` de `.paramrig` ; dis pourquoi.
- **Tests** : `services/web/server.test.mjs` pour le seed refusé dans un répertoire qui n'est pas vide et accepté dans un répertoire vide (ou pour le profil, selon le choix), pour le `.gitignore` écrit une seule fois et jamais réécrit, et un passage réel : pointer le service sur un dossier temporaire avec un `package.json` et sans manifeste, ouvrir `/web`, lire le message.
